# Setup CCS Web Server — Node.js Web Server

This section provides an example of how to set up a basic **CCS Web Server** using **Node.js**.

The example uses `server.js` as the CCS Web Server. It provides the interface between the end user's browser and the **xstAuth Light Server**, handling the authentication request and redirecting the user to the xstAuth sign-in or sign-up flow.

> **Note:** This is a basic example. Your CCS Web Server may require additional files, directories, packages, or configuration depending on your implementation.

## 1. Create the Node.js Project

Start **VS Code** and open a new window.

Open a new terminal and `cd` into the previously created `CCS_WebServer` directory:

```powershell
cd CCS_WebServer
```

### Verify Node.js and npm

Verify that **Node.js** and **npm** are installed and available from PowerShell:

```powershell
node --version
npm --version
```

If both commands return a version number, continue with the project setup.

Run:

```powershell
npm init -y
npm install express cookie-parser jsonwebtoken dotenv
```

These commands create the basic Node.js web server project.

The following are generated automatically by npm:

* `package.json`
* `package-lock.json`
* `node_modules`

## 2. Add the CCS Web Server Files

Move the provided `server.js` and `env-example` files into the `CCS_WebServer` directory.

The resulting project structure should be similar to:

```text
CCS_WebServer/
│
├── node_modules/
├── env-example
├── HTTP-01.js
├── HTTPS-01.js
├── package-lock.json
├── package.json
└── server.js
```

Rename:

```text
env-example
```

to:

```text
.env
```

If VS Code prompts you to trust the folder, select **Trust Folder & Continue**.

## 3. Configure TLS Certificates

Configure the `.env` file to reference the TLS certificate files generated by **win-acme (WACS)**.

For example:

```text
PRIVATE_KEY=C:/xstAuth/certs/ccs.yourdomain.com-key.pem
CERTIFICATE=C:/xstAuth/certs/ccs.yourdomain.com-crt.pem
# INTERMEDIATE_CHAIN=C:/xstAuth/certs/ccs.yourdomain.com-chain-only.pem
# FULL_CHAIN=C:/xstAuth/certs/ccs.yourdomain.com-chain.pem
```
Use the actual certificate file paths and filenames generated on your server.

Your implementation may only require `PRIVATE_KEY` and `CERTIFICATE`. The exact environment variable names and certificate files required depend on your CCS Web Server implementation.

Check the certificate files generated by **win-acme (WACS)** in:

```text
C:\xstAuth\certs
```

> **Important:** Do not assume that the filenames shown above are identical to those generated on your server. Always use the actual paths and filenames present in `C:\xstAuth\certs`.

> **Security:** Never publish a `.env` file containing passwords, private keys, authentication secrets, or other sensitive configuration values to a public repository. Keep private keys secure and never commit them to source control.

## 4. Configure xstAuth Light Server Credentials

Obtain the following information from the **xstAuth Light Server**:

* JWT public key — Complete
* Client ID
* Client Secret
* mTLS key — Complete
* mTLS certificate — Complete
* mTLS CA certificate — Complete

The mTLS credentials configured in the CCS Web Server must exactly match the corresponding mTLS configuration on the **xstAuth Light Server**.

### Sample mTLS Credentials

In the previous steps in `05_Generate_RSA_Key_Pairs.md`, you moved the downloaded test PEM files into the `C:\xstAuth\CCS_mTLS` directory.

The directory should already contain:

```text
C:/xstAuth/CCS_mTLS/mtlsKey.pem
C:/xstAuth/CCS_mTLS/mtlsCert.pem
C:/xstAuth/CCS_mTLS/mtlsRootCA.pem
C:/xstAuth/CCS_mTLS/publicKeyJWT.pem
```

Confirm or add the correct paths to the `.env` file.

For example:

```text
mTLSKEY=C:/xstAuth/CCS_mTLS/mtlsKey.pem
mTLSCERT=C:/xstAuth/CCS_mTLS/mtlsCert.pem
mTLSCA=C:/xstAuth/CCS_mTLS/mtlsRootCA.pem

JWT_PUBLIC_KEY=C:/xstAuth/CCS_mTLS/publicKeyJWT.pem
```

> **Security:** The sample mTLS credentials and JWT public key are provided for testing and demonstration purposes only. For production use, generate and configure your own mTLS credentials and JWT signing key according to your security requirements. Never publish private keys, signing keys, or other sensitive credentials.
>
> A guide for generating your own mTLS credentials and JWT signing key is provided on the **How to Setup** page, available under the **Help** menu in the **xstAuth Light Server**.

### Client ID and Client Secret

Obtain a new **Client ID** and **Client Secret** from the **xstAuth Light Server** and add them to the `.env` file.

Ensure that the **Client ID** and **Client Secret** in `.env` match the latest credentials obtained from the **xstAuth Light Server**.

For example:

```text
CCS_CLIENT_ID='your-client-id'
CCS_CLIENT_SECRET='your-client-secret'
```

> **Security:** Treat the Client Secret as confidential. Do not publish it in source code, documentation, screenshots, or public repositories.

## 5. Configure the CCS Web Server

Open `server.js` and check the following configuration values.

Replace `ccs.com` and `auth.ccs.com` with the appropriate domains for your deployment.

```javascript
const CCS_LANDING_PG_URL = "https://www.ccs.com";
const AAS_BASE_URL = "https://auth.ccs.com/authenticate";
const CCS_BASE_URL = "https://www.ccs.com/code-exchange";

// Locate line 175 and find:
res.cookie("state", `${response.state}`, {  
  domain: "ccs.com", // Replace with your own parent domain (e.g., itmarket.com)
```

Also check the private hostname used for the mTLS connection:

```javascript
const AAS_PRIVATE_URI = "aas.private.io";
```

> For the sample test environment, `aas.private.io` is the default hostname used by the test mTLS certificates.
>
> If using your own mTLS certificates and private hostname, replace this value with the appropriate private hostname for your **xstAuth Light Server**.

If the configuration values are correct, click **Save All**. The **CCS Web Server** configuration is now complete and ready for final testing.

## 6. Start the CCS Web Server

Make sure you are in the correct directory, then start the server from the VS Code terminal:

```powershell
cd CCS_WebServer
node server.js
```

### Verify hostname resolution 

After starting the server, open a separate Windows PowerShell window and verify that both hostnames resolve correctly. The returned addresses should correspond to the private IP addresses of the appropriate servers.

```powershell
ping ccs.private.io
ping aas.private.io
```
> **Note:** If a `ping` test fails, this does not necessarily mean that hostname resolution or network connectivity has failed. Some environments block ICMP traffic used by `ping`. Use `Test-NetConnection` to verify TCP connectivity on port 8443 from the CCS Web Server to the xstAuth Light Server.

Verify TCP connectivity on port 8443

Assumption: xstAuth Light Server is still running.

> Test-NetConnection aas.private.io -Port 8443

Look for:

> TcpTestSucceeded : True

This confirms that the CCS Web Server can establish a TCP connection to the xstAuth Light Server on port 8443.

If TcpTestSucceeded is False, check the private DNS or hosts file configuration and Windows Firewall rules on both servers. A failed ping does not necessarily indicate a connectivity failure, as some environments block ICMP traffic.

At this point, final server-side testing is complete. Proceed with end-to-end authentication testing.

Refer to [`08_Test_Run.md`](08_Test_Run.md).
